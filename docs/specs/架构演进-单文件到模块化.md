# 架构演进：单文件 HTML → Vite + 模块化

## Problem Statement

当前系统是一个单文件 HTML（`index.html`, 67KB），逆变器配置数据、样式、业务逻辑全部耦合在一起。随着业务扩展（新增 780~785W 组件系列、湖南专用配置），维护成本持续上升，尤其是**修改逆变器配置数据非常麻烦**——需要在 67KB 的 HTML 中搜索定位并手动编辑硬编码数据。

同时，未来规划**全国推广 + 更多组件型号**，当前架构无法支撑可持续的迭代。团队为单人维护，系统已部署在 GitHub Pages，不接受引入后端服务。

## Solution

采用渐进式架构演进，在**保持纯前端 + GitHub Pages 部署**的前提下，将单文件拆分为模块化结构，引入 Vite 构建系统，并建立自动化数据验证和单元测试体系。

整体分三个 Phase 执行，每 Phase 可独立部署上线。

### Phase 1：Vite 构建 + 数据/代码分离

- 引入 Vite 构建系统，支持 `npm run dev`（热更新开发）和 `npm run build`（生产构建）
- 将 CSS 从内联分离到 `src/css/style.css`
- 将逆变器配置数据（DB、HUNAN_DB、ZHANGJIAJIE_DB）从 HTML 抽离到 `src/js/data/` 下独立文件
- 将线缆规格表（CABLE_THRESHOLDS）抽离到 `src/js/data/cables.js`
- 配置 GitHub Actions 自动构建并部署到 GitHub Pages

### Phase 2：代码分层 + 数据验证 + 单元测试

- JS 按功能拆分为 search/matching/render 等模块
- 编写 `scripts/validate-data.js`，在构建时自动检查数据完整性
- 引入 Vitest，为核心匹配逻辑（matching.js）编写单元测试
- 修正区域数据管线的数据源指向（改为"全国并网箱&逆变器配置统计.xlsx → 全国省市区列表"）

### Phase 3：数据治理

- 整理 Excel 源文件到 `data/` + `archived/` 目录
- 统一文件命名规范

## User Stories

1. 作为开发者，我希望运行 `npm run dev` 启动开发服务器（热更新），以便快速迭代代码
2. 作为开发者，我希望运行 `npm run build` 自动完成构建，以便一键生成生产版本
3. 作为开发者，我希望逆变器配置数据从 HTML 中分离到独立的 JS 文件，以便修改数据时不需要在 67KB 文件中搜索
4. 作为开发者，我希望 CSS 从内联分离到独立文件，以便样式独立维护
5. 作为开发者，我希望新增组件系列时只需在数据文件中追加一条记录，以便降低出错概率
6. 作为开发者，我希望构建时自动运行数据完整性验证（连续性、边界、重复检查），以便在部署前发现问题
7. 作为开发者，我希望核心匹配逻辑有单元测试覆盖，以便重构时能快速发现回归问题
8. 作为开发者，我希望 `npm run build` 在构建前自动执行数据转换和验证，以便简化操作流程
9. 作为开发者，我希望推送到 main 分支后 GitHub Actions 自动构建并部署到 Pages，以便减少手动操作
10. 作为开发者，我希望搜索/级联逻辑（search.js）、匹配逻辑（matching.js）、渲染逻辑（render.js）各自独立，以便每个模块的代码量控制在 300 行以内
11. 作为开发者，我希望区域数据转换脚本的数据源指向"全国并网箱&逆变器配置统计.xlsx → 全国省市区列表"，以便与实际权威数据源对齐
12. 作为开发者，我希望 `CLAUDE.md` 中记录完整的命令和更新流程，以便快速上手
13. 作为开发者，我希望 Excel 源文件统一放在 `data/` 目录、旧版移入 `archived/`，以便避免版本混乱

## Implementation Decisions

### 构建系统
- **Vite**：零配置启动，原生支持 ES Module，构建产物为纯静态文件（dist/），与 GitHub Pages 完美兼容
- **npm scripts**：定义 dev/build/convert/validate/deploy 等命令，统一入口
- **GitHub Actions**：push 到 main 自动触发构建 + 部署，构建产物发布到 Pages

### 目录结构
```
src/
├── index.html               ← 视图入口（不含数据）
├── css/style.css             ← 样式独立
└── js/
    ├── main.js              ← 初始化、事件绑定、模块协调
    ├── search.js             ← 搜索、拼音匹配、级联联动
    ├── matching.js           ← 核心匹配逻辑
    ├── render.js             ← 结果渲染
    └── data/
        ├── region-data.js    ← 区域容配比（自动生成）
        ├── inverters.js      ← 逆变器配置表（手动维护）
        ├── hunan.js          ← 湖南/张家界专项（手动维护）
        ├── cables.js         ← 线缆规格（手动维护）
        └── constants.js      ← 共享常量
scripts/
├── convert-all.js            ← Excel → region-data.js
└── validate-data.js          ← 数据完整性验证
data/                         ← Excel 源文件
archived/                     ← 旧版 Excel
```

### 数据分离
- 逆变器/湖南/线缆数据**保持手动维护**，不纳入自动化管线
- 区域容配比数据通过 `npm run convert` 从 Excel 自动生成
- 每个数据文件使用 ES Module 格式 `export const`，Vite 构建时自动打包

### 部署
- 构建产物部署 `dist/` 到 GitHub Pages（根目录有 index.html，完全符合 Pages 要求）
- 两种方式：① GitHub Actions 自动部署（推荐） ② `npx gh-pages -d dist` 手动部署

## Testing Decisions

### 测试策略
- **不做** E2E 测试（已有 Playwright 测试但不在本 spec 范围）
- **不做** 纯手动测试
- **核心原则**：只测外部行为，不测实现细节

### 测试切入点

#### 1. 数据完整性验证（`scripts/validate-data.js`）
- 在 `npm run build` 的 `prebuild` 阶段自动运行
- 检查项：
  - 每个容配比下的组件数量挡位是否连续无缺口
  - 最小/最大挡位是否覆盖合理范围（如 10~330）
  - 湖南配置的所有挡位是否在标准表对应范围内
  - 同一系列+容配比+挡位是否有重复条目
  - 区域数据键格式是否为"省份-城市-区县"
- 不通过则构建失败，防止错误数据上线

#### 2. 单元测试（Vitest）
- 测试框架：Vitest（与 Vite 共享配置，零额外配置成本）
- 测试对象：`matching.js` 的核心函数（`lookupMatch`, `lookupCable`, 容配比映射）
- 数据文件使用实际数据而非 mock，确保测试真实反映生产行为
- 用例示例：
  - 给定特定组件系列+数量+容配比，返回正确的逆变器组合和并网箱功率
  - 张家界地区优先走 ZHANGJIAJIE_DB
  - 湖南非张家界地区走 HUNAN_DB
  - NEG21_730 系列走标准表的 730 分支
  - 线缆查表：功率小于第一个挡位应返回最小规格
  - 线缆查表：功率超过最后一个挡位应返回最大规格
  - 湖南地区限制只显示 NEG21_730 系列

### 已有测试文件（继续保留，但不改动）
- `test-hunan.js`（Playwright E2E 测试，14 个用例，已全部通过）
- `test-verify.js`（Node.js 验证测试）

## Out of Scope

- **逆变器/线缆数据自动化管线**：DB、HUNAN_DB、CABLE_THRESHOLDS 数据保持手动编辑，不纳入 Excel 自动转换
- **E2E 测试改造**：现有 Playwright 测试不动，不做新增
- **引入后端/数据库**：保持纯前端架构不变
- **迁移到 React/Vue 等框架**：保持原生 JS，不与当前实现方式做重大偏离
- **Excel 源文件的大版本管理方案**：仅做物理位置整理，不做自动化版本管理
